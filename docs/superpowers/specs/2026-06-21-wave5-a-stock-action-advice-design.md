# Wave 5-A 종목 액션 제언 설계

## 목표

보유 종목과 관심 종목 각각에 대해 “지금 어떻게 할지”를 방향·비중·구간·근거·신뢰도까지 포함해 제시한다.  
핵심 원칙은 다음 셋이다.

- 숫자는 코드가 결정한다.
- LLM은 숫자를 만들지 않고 해석만 한다.
- 재료가 갈리면 갈리는 그대로 보여 주고, 가짜 확신을 만들지 않는다.

이 레이어는 화면 표시 전용이며 자동 주문 경로는 만들지 않는다.

---

## 접근 방식 검토

### 접근 1 — 저장형 판단 레이어 + 결정론 숫자 + LLM 서술

권장안이자 이번에 채택한 방식이다.

- `stock_action_advice` 테이블에 종목별 제언을 `asof`별로 누적 저장한다.
- 방향, 현재 비중, 목표 비중 레인지, 진입/이탈 후보 구간은 코드가 산출한다.
- Gemini 상위 모델은 “왜 이런 판단이 나왔는지”, “재료가 어디서 갈리는지”, “구간을 어떻게 읽어야 하는지”만 서술한다.

장점:

- 과거 제언 이력 보존과 사후 검증이 가능하다.
- 숫자 책임이 코드에 있어 재현성과 통제가 좋다.
- “임의 숫자 금지”와 “모든 숫자에 출처 재료 명시”를 지키기 쉽다.

단점:

- 룰 테이블 설계를 먼저 잘 해야 한다.
- 첫 버전은 숫자 표현이 다소 보수적일 수 있다.

### 접근 2 — export 파생형

매 실행마다 export에서 제언을 바로 계산해 화면에만 보이게 하는 방식이다.

장점:

- 스키마 추가 없이 빠르다.

단점:

- 과거 제언의 보존과 검증이 어렵다.
- 모델·기준일·근거 비교가 약하다.

이번 기능은 판단 레이어의 검증과 이력 추적이 핵심이므로 제외한다.

### 접근 3 — LLM이 숫자까지 산출

비중 레인지와 진입/이탈 구간까지 모델이 내게 하는 방식이다.

장점:

- 더 유연해 보인다.

단점:

- 임의 숫자 생성 위험이 높다.
- 근거 추적과 회귀 검증이 나빠진다.
- “결정론 가능한 부분은 코드로” 원칙과 충돌한다.

이번 작업에서는 명시적으로 금지한다.

## 최종 설계

### 1. 저장 계약

새 테이블 `stock_action_advice`를 추가한다.

컬럼:

- `ticker TEXT NOT NULL`
- `asof DATE NOT NULL`
- `direction TEXT NOT NULL CHECK (direction IN ('매수', '비중확대', '유지', '비중축소', '매도'))`
- `current_weight NUMERIC`
- `target_weight_low NUMERIC`
- `target_weight_high NUMERIC`
- `weight_action TEXT NOT NULL CHECK (weight_action IN ('늘림', '유지', '줄임'))`
- `entry_zone TEXT`
- `exit_zone TEXT`
- `confidence TEXT NOT NULL CHECK (confidence IN ('상', '중', '하'))`
- `rationale TEXT NOT NULL`
- `supporting_factors JSONB NOT NULL DEFAULT '[]'::jsonb`
- `opposing_factors JSONB NOT NULL DEFAULT '[]'::jsonb`
- `divergence_note TEXT`
- `model TEXT`
- `created_at TIMESTAMPTZ NOT NULL DEFAULT now()`

제약:

- 누적 저장이 원칙이므로 덮어쓰기 대신 날짜별 이력을 남긴다.
- 같은 종목의 같은 날짜에 같은 파이프라인 실행이 중복 적재되지 않도록 `UNIQUE (ticker, asof)`를 둔다.
- 만약 같은 날 재실행이 필요하면 같은 기준일에 대한 재생성은 upsert로 최신 내용만 유지하고, 날짜별 이력은 계속 보존한다.
- 즉, 이력 단위는 **하루 1건**이다. 이 테이블은 “일 단위 시계열로 사후검증”하기 위한 기준 레이어다.

이 테이블은 “과거 제언이 맞았는지”를 나중에 검증할 기준 레이어다.

---

### 2. 숫자 산출 책임 분리

#### 2-1. 현재 비중

현재 비중은 실행 시 코드로 파생한 뒤, 당시 판단 기준을 보존하기 위해 `stock_action_advice.current_weight`에 함께 저장한다.

- 보유 종목:
  - `current_weight = eval_amount / asset_total`
- 비보유 관심 종목:
  - `current_weight = 0`

입력 원천:

- `portfolio`의 종목별 `eval_amount`
- `portfolio_snapshot.payload.asset_total`

둘 모두 읽기 경계에서 float 변환한다.

저장 이유:

- 이후 “그 시점에 얼마 비중이었기에 확대/축소를 권했는지”를 검증할 수 있어야 하기 때문이다.

#### 2-2. 목표 비중 레인지

목표 비중 숫자는 LLM이 만들지 않는다.  
코드가 결정론적으로 산출한다.

입력 변수:

- 보유 여부
- 표시 신호 (`매수` / `관망` / `축소`)
- 현 국면 (`bull` / `neutral` / `bear`)
- 신뢰도 (`상` / `중` / `하`)
- 컨센서스 괴리율

산출 방식:

- 우선 내부 등급 `allocation_band`를 계산한다.
- 그 등급을 최종 레인지 `%`로 매핑한다.
- 단일 종목 과집중 방지 상한을 코드에 둔다.

초기 밴드 제안:

- `exit` → `0–1%`
- `starter` → `0–3%`
- `build` → `3–6%`
- `core` → `6–10%`

초기 상한:

- 어떤 경우에도 `target_weight_high > 10%` 금지
- bearish 국면에서는 기본적으로 `core` 금지
- `축소` 신호에서는 `build/core` 금지

초기 규칙 예시:

- 비보유 + 매수 + 신뢰도 상 + bull/neutral + 괴리율 양수 충분 → `starter` 또는 `build`
- 보유 + 매수 + 신뢰도 상 + bull + 재료 일치 강함 → `build` 또는 `core`
- 보유 + 관망 + 재료 혼조 → 현재 비중 근처 유지, 밴드는 현재 수준을 크게 넘지 않음
- 보유 + 축소 또는 bearish + 단기 악재 우세 → `starter` 또는 `exit`

중요한 점은 이 규칙이 코드 테이블/함수로 명시되어야 한다는 것이다.  
“모델이 느낌으로 정한 숫자”는 허용하지 않는다.

또한 어떤 변수가 어떤 밴드 결정을 밀었는지는 `supporting_factors`에 구조화해 기록한다.

예시:

```json
[
  {"source":"퀀트신호","value":"매수","effect":"build 상향"},
  {"source":"국면","value":"bull","effect":"상한 허용"},
  {"source":"신뢰도","value":"중","effect":"core 금지"},
  {"source":"컨센서스 괴리율","value":"+18%","effect":"신규 진입 정당화"}
]
```

#### 2-3. 진입/이탈 구간

진입/이탈 구간도 코드가 후보를 도출하고 LLM은 해석만 한다.

허용 근거:

- 주요 이동평균 (`SMA20/60/120`)
- 최근 지지/저항 후보
- 목표가 대비 괴리율
- 현재가와의 기술적 위치

초기 원칙:

- 근거가 충분치 않으면 구간을 비워 둔다.
- 단순 임의 숫자 금지.
- `entry_zone` / `exit_zone`은 화면 표시용 문자열로 저장하되, 그 뒤에는 반드시 근거가 있어야 한다.

예:

- `entry_zone = "SMA60 부근 재확인 시"`
- `exit_zone = "목표가 근접 또는 SMA20 이탈 시"`

첫 버전에서는 숫자 자체보다 “근거 기반의 해석 가능한 구간”에 더 무게를 둔다.

---

### 3. 신뢰도와 divergence

신뢰도는 단일 합산 점수가 아니라 재료 일치도로 산출한다.

입력 재료:

- 퀀트신호
- 현 국면에서의 백테스트 성과
- 컨센서스 괴리율/의견
- 뉴스 심리
- 수동 AI 분해(단/중/장)
- 드라이버(원자재/업종 프록시)
- 매크로

산출 원칙:

- 서로 같은 방향을 지지하는 재료가 많고 반대 재료가 적으면 `상`
- 찬반이 섞이면 `중`
- 핵심 재료가 강하게 충돌하거나 데이터가 빈약하면 `하`

하지만 이 역시 “숫자 점수 72점” 같은 형태로 저장하지 않는다.  
최종 저장 값은 `상/중/하`이고, 왜 그런지는 `supporting_factors`, `opposing_factors`, `divergence_note`에 분해해 남긴다.

예시:

- 퀀트·컨센서스는 강세
- 단기 드라이버는 약세
- 수동분해는 장기 강세/단기 보수

이 경우:

- `confidence = 중`
- `divergence_note = "퀀트·컨센서스는 강세지만 단기 드라이버와 단기 외부자료는 보수적이어서 변동성 구간으로 해석"`

---

### 4. LLM 역할

LLM은 상위 모델을 사용하되, 역할은 서술에 한정한다.

입력:

- 코드가 계산한 숫자 결과
- 각 숫자의 근거 메타데이터
- 종목의 자동 수집/수동 분석/거시/드라이버 재료

출력:

- `rationale`
- `divergence_note`
- `supporting_factors` / `opposing_factors`에 들어갈 구조화 요약
- 진입/이탈 구간의 해석 문장

금지:

- 목표 비중 low/high 숫자 생성·수정
- 진입/이탈 구간 숫자 창작
- 근거 없는 확신 문장
- 자동 주문으로 오해될 수 있는 집행 지시

모델 프롬프트에는 아래를 강하게 명시한다.

- 숫자는 입력으로 받은 값만 사용하라.
- 새로운 숫자나 가격대를 만들지 마라.
- 재료가 갈리면 갈리는 그대로 적어라.
- 근거가 약하면 약하다고 말하라.

### 5. 파이프라인 편입

06시 전체 실행에 `stock_action_advice` 종합 단계를 추가한다.

순서:

1. 가격/지표/퀀트/뉴스/컨센서스/수동분해/거시/드라이버가 모두 준비된 뒤
2. 종목별 액션 제언 컨텍스트를 조립
3. 숫자와 구간 후보를 코드가 먼저 계산
4. 상위 모델로 서술만 생성
5. `stock_action_advice`에 저장

안정성 규칙:

- 종목별 `try/except` 격리
- Gemini timeout·배치예산 준수
- 예산 초과 시 남은 종목은 다음 실행으로 이월
- 한 종목 실패가 전체 파이프라인을 멈추지 않음

배치 예산 전략:

- 이미 존재하는 상위 모델 상수(`GEMINI_MANUAL_RESEARCH_MODEL`)를 재사용
- 종목별 호출 전에 남은 예산 시간을 확인
- 예산 초과 시 `runs.errors`에 “action_advice budget exceeded” 성격의 기록을 남기고 종료

이 기능은 고비용 경로이므로 대량 뉴스 선별처럼 전 종목에 무제한 호출하지 않는다.

---

### 6. export 계약

종목별 export에는 최신 1건과 최근 이력을 함께 제공한다.

최신:

- `actionAdviceLatest`

이력:

- `actionAdviceHistory`

조회 원칙:

- 종목별 최신 조회만 사용
- 글로벌 `max(asof)` 금지

포함 필드:

- 방향
- 현재 비중
- 목표 비중 low/high
- 조정 방향
- 진입/이탈 구간
- 신뢰도
- 지지/반대 재료
- divergence note
- 기준일
- 모델

### 7. UI 설계

종목상세 탭에 “액션 제언” 카드를 추가한다.

기본 표시:

- 방향 뱃지
- 현재 비중 → 목표 비중 레인지
- 조정 방향(늘림/유지/줄임)
- 진입 구간 / 이탈 구간
- 신뢰도
- 지지 재료 / 반대 재료
- divergence note

기본은 최신 1건만 표시한다.

과거 보기:

- 토글로 `actionAdviceHistory`를 펼친다.
- 이후 “제언 정확도 검증”의 바탕이 되도록 과거 기준일과 방향, 비중, 신뢰도를 읽을 수 있게 한다.

화면 문구 원칙:

- “근거 기반 제안”이라는 톤 유지
- 자동 집행 뉘앙스 금지
- 숫자 옆에는 가능한 한 어떤 재료에서 왔는지 드러나게 한다

### 8. 테스트 전략

#### 백엔드

- 목표 비중 밴드 규칙 함수 단위 테스트
- 과집중 상한 테스트
- 비보유 종목 현재 비중 0 테스트
- 진입/이탈 구간 후보 생성 테스트
- confidence/divergence 분류 테스트
- export가 최신/이력 모두 붙이는지 테스트

#### LLM 가드

- 프롬프트/파서 테스트로 숫자 필드가 LLM 출력으로부터 오염되지 않는지 확인
- 숫자 없이 서술만 들어와도 저장 가능한지 확인

#### UI

- 액션 제언 카드 렌더 테스트
- 이력 토글 테스트
- 방향/신뢰도/현재→목표 비중 표시 테스트

#### 스모크

- 실제 보유 종목 1개에 대해
  - 방향
  - 현재 비중
  - 목표 비중 레인지
  - 진입/이탈 구간
  - 지지/반대 재료
  - 신뢰도
  전체가 출력되는지 확인한다.
- 추가로 전체 대상 중 `entry_zone` 또는 `exit_zone`이 실제로 채워진 종목 비율을 보고한다.
- 비어 있는 경우는 원인을 구분해 보고한다.
  - 데이터 부족
  - 보수적 규칙에 따라 구간 미제시

## 대상 우선순위와 비용 통제

상위 모델 호출은 전 종목 매일 실행하지 않는다.

우선순위:

1. **보유 7종목 매일 보장**
2. **관심종목 중 신호 변화 또는 뉴스 이벤트가 있는 종목**
3. **나머지 종목은 배치예산 잔여분 내에서 수행하거나 순환(며칠 주기)**

운영 원칙:

- 전 종목 매일 상위 모델 호출 금지
- 보유 종목은 예산보다 우선한다
- 남은 예산이 부족하면 저우선순위 종목은 다음 실행으로 이월한다
- `runs.errors`에 예산 초과와 이월 사실을 남긴다

파이프라인 구현 시에는 먼저 대상 리스트를 우선순위별로 구성한 다음, 남은 예산 시간/호출 여유를 확인하면서 순차 처리한다.

## 구현 시 주의사항

- DB NUMERIC은 읽기 경계에서 float 변환
- 종목별 최신 조회는 종목 단위 latest 패턴 유지
- 현재 비중은 저장이 아니라 파생이 원칙
- raw 수동분해/내 판단/자동수집은 합산 점수로 묶지 않는다
- 신뢰도는 `상/중/하`와 divergence 노트로 드러내고 숫자 스칼라 하나로 뭉개지 않는다
- 숫자는 코드 책임, LLM은 서술 책임
