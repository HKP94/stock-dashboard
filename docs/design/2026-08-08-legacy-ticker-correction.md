### 1-2. 실제 피해 — 이미 틀린 값이 DB에 있다

**① 베타 오계산 (078350 한양디지텍)**

접미사도 `.KS`라 코스닥 종목인데 **^KS11(코스피) 기준으로 베타 1.152가 계산·저장돼 있다.**

"allowlist라는 별도 진실원본"이 드리프트한다는 R4 진단의 실증이다.

**② 뉴스 소스 오분류 (278470.KR APR)**
`ingest_news._is_kr("278470.KR")` = **False** → 한국 종목인데 **US 뉴스 경로**로 수집 중.
영문 소스만 긁고 네이버 한글 뉴스를 놓친다.

**③ 발굴 후보 재부상 (discovery)**
`discovery_screen`에 `213420.KQ`·`278470.KS`가 **`in_watchlist=False`** 로 4주 연속 적재됨.
이미 관심종목인데 "새로 발굴된 종목"으로 표면화되고 있다.

## 2. 설계 결정 — 왜 '제거+추가'가 아니라 'UPDATE(rename)'인가

`CLAUDE.md`의 기존 관례는 **"티커 정정 = 제거+추가"**(`POST /api/watchlist/{old}/correct`)다.
**이번은 그 관례를 따르지 않는다.** 근거:

| | 기존 관례가 상정한 상황 | 이번 상황 |
|---|---|---|
| 데이터 성격 | 오타 티커로 쌓인 **잘못된 데이터** | `059090.KS`의 1,261개 가격은 **진짜 미코 가격** |
| 옳은 처리 | 버리고 새로 백필 | **레이블만 교정**, 데이터는 보존 |
| 비용 | 백필 재수집 | 0 (UPDATE) |
| 손실 | 없음(원래 쓰레기) | 제거+추가 시 **이력 11,048행 소실** |

즉 관례의 *목적*(잘못된 데이터가 올바른 티커에 붙는 것 방지)은 여기서 발생하지 않는다 —
데이터와 종목의 대응은 처음부터 맞았고, 표기만 틀렸다. **관례에서 벗어나는 판단이므로 PM 승인 대상**으로 명시한다.
승인되면 `CLAUDE.md`에 "오타 정정(제거+추가) vs 표기 정정(rename)" 구분을 추가한다.

## 3. 마이그레이션 설계

### 3-1. 파일: `migrations/s1_legacy_ticker_rename.sql`

```sql
-- 멱등: 대상 티커가 이미 정정됐으면 0행 UPDATE(재실행 안전)
-- ticker 컬럼 보유 18개 영향 테이블을 명시적으로 나열한다.
--   ★동적 SQL(information_schema 순회) 금지 — 스키마가 늘 때 조용히 새 테이블을 건드리는
--     것보다, 명시 목록이 리뷰 가능하고 의도가 드러난다.
UPDATE prices_daily SET ticker='059090.KQ' WHERE ticker='059090.KS';
... (18 테이블 × 5 rename)
```

- **트랜잭션 1개**로 전체 실행(부분 적용 방지). 실패 시 전량 롤백.
- **140610은 rename하지 않는다** — 코넥스는 `.KS`/`.KQ` 어느 쪽도 아니다.
  `watchlist.active=false`만 설정(데이터 보존, export에서 자연 소멸).
- 마이그레이션 글롭이 매 빌드 재실행되므로 **멱등성 필수**(WHERE 조건이 이를 보장).

### 3-2. 실행 순서 (역순 불가 — 순서가 정합성을 만든다)

1. **사전 스냅샷**: 대상 티커별 테이블 행 수를 기록(사후 대조용)
2. 마이그레이션 실행(단일 트랜잭션)
3. **사후 검증**: 이동 행 수 == 사전 스냅샷, old 티커 잔존 0행
4. `_KOSDAQ_DEFAULT` 정리(§3-3) + 코드/테스트 갱신
5. **quant 재계산** — 078350의 벤치마크가 `^KS11`→`^KQ11`로 바뀌므로 beta/market_corr 재산출 필요
6. **export 재생성** → 화면 반영

### 3-3. 코드 참조 갱신

| 위치 | 현재 | 조치 |
|---|---|---|
| `compute_quant._KOSDAQ_DEFAULT` | `{059090, 213420, 338220}` | **비운다** — rename 후 접미사가 유일 판정 근거. 별도 진실원본을 남기면 078350 같은 드리프트가 재발한다 |
| `tests/test_fx_and_kosdaq.py` | `_market_benchmark("059090.KS")==^KQ11` | `.KQ` 티커 기준으로 갱신 |
| `tests/test_market_beta.py` | 동일 + `"059090" in codes` | 동일 |
| `scripts/kb_supply_pilot.py` | `("059090.KS","미코")` | `.KQ`로 |
| `CLAUDE.md` §KR 티커 접미사 | "레거시 3종은 allowlist가 커버" | "정정 완료, allowlist 불필요"로 갱신 |

**`KOSDAQ_TICKERS` env는 보존** — 외부 운영자가 임시 보정할 여지(코드 배포 없이).

### 3-4. 회귀 가드 (신규 테스트)

- `watchlist`의 모든 KR 티커 접미사가 실제 시장과 일치하는지 **주기 점검 가능한 순수 함수**
  (KB 조회는 테스트에서 못 하므로, 고정 픽스처로 매핑 규칙만 검증)
- rename 후 `_market_benchmark`가 allowlist 없이도 4종목 전부 `^KQ11`을 주는지
- `_is_kr("278470.KS")` == True

## 4. 묶음 처리 — KR 일정 28행 덤프 정리 (R7 후속)

**문제**: `earnings.upcoming` 31건 중 28건이 `2026-08-14` 동일일자 KR 추정행이라
US 확정일정(LITE 8/11 · SPCE 8/12 · FUTU 8/19)이 파묻힌다.

**설계**:
- export가 `confirmed=false` + 동일 `scheduled_date` KR 건을 **1행으로 집약**:
  ```json
  {"kind": "group", "label": "KR 반기보고서 법정기한", "scheduled_date": "2026-08-14",
   "count": 28, "confirmed": false, "tickers": [...]}
  ```
- 라벨을 **'예정일'이 아니라 '법정기한'**으로 명시(오해 방지 — PM 지시).
- DART 실접수가 잡히면 `confirmed=true`·`reported=true`로 승격되어 **자동으로 개별 행**이 된다
  (현 upsert 방어 유지 — 추가 코드 불필요).
- 집약은 **export 표시 레이어 전용**. `earnings_calendar` 원본은 종목별 행 그대로(조회·트리거용).
