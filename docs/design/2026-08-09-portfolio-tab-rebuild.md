## 1. P① 원인 확정 — "배선 누락"이 아니라 **한 수식에 소스가 3개**

### 재현 (라이브 DOM 25ms 간격 샘플링)

```
ms 1029:  현금 (₩) ₩0          = 총자산 (₩) ₩8,784,009    ← 자기모순 구간
ms 2002:  현금 (₩) ₩4,758,128  = 총자산 (₩) ₩8,784,009    ← 정상 복구
```

`/api/cash`는 정상값(`[{currency:"KRW", amount:4758128.0}]`)을 준다. **API는 무죄다.**

### 진짜 원인

수식 세 항이 **서로 다른 출처에서 서로 다른 시점에** 도착한다:

| 항 | 값 소스 | 도착 시점 |
|---|---|---|
| 주식 평가액 | `rows` (`GET /api/portfolio`) → 클라이언트가 직접 합산 | 1번째 |
| **현금** | `cashRows` (`GET /api/cash`) → 클라이언트가 직접 합산 | **2번째** |
| 총자산 | `portfolioAssetTotal(summary)` — 초기값이 `D.portfolio`(data.json) | **0번째(즉시)** |

`loadPortfolio`가 세 fetch를 **순차 await** 하는데(`tabsC.jsx:56~66`), `setRows()`가 먼저 반영되면
`hasAny`가 true가 되어 수식 블록이 렌더된다. 이때 총자산은 data.json에서 이미 있고 현금만 `[]`다
→ **주식 O + 현금 ₩0 + 총자산 O**. PM이 본 화면이 정확히 이 프레임이다.

### 수정안 — 소스를 하나로 (§8-1 "같은 값의 소비 경로 전부 grep")

`/api/portfolio/summary` 한 응답이 **세 항을 모두, 서로 정합하게** 가지고 있다:

```
total_eval  4,025,880.89   cash_total  4,758,128.0   asset_total  8,784,008.89
                                    (4,025,881 + 4,758,128 = 8,784,009 ✓)
```

→ 수식 3항 전부 `summary`에서 읽는다. **클라이언트 합산(`totalEvalKrw`·`cashKrw`·`toKrw`)을 삭제**한다.
한 객체에서 나오므로 세 항이 시점에서 갈릴 수 **구조적으로** 없다. 코드도 줄어든다(순삭 ~20줄).
`rows`·`cashRows`는 **표 렌더 전용**으로 남긴다.

추가로 `summary`가 아직 없을 때는 수식 블록을 **렌더하지 않는다**(스켈레톤). 틀린 숫자를
잠깐 보여주느니 잠깐 비우는 게 낫다 — 돈 화면에서 0은 "없음"으로 읽힌다.

> 회귀 가드: `display.js`에 순수함수 `assetEquation(summary)`를 두고, **세 항 합 정합**과
> **결측 시 null 반환**(0 반환 금지)을 테스트로 고정한다.

## 2. P② 스테일 전략 조언

### 현황

```
generatedAt   2026-07-01T00:12   (39일 전)
stale         true               ← export가 이미 판정 중
holdingsCount 6                  ← 당시 6종목 / 현재 4종목
cacheKey      ce12ce9dee8d8674   ← 불투명 해시. 티커 복원 불가
```

본문은 옛 총자산 `10,066,443`과 옛 보유를 서술한다. 현재 UI는 **경고 1줄 + 본문 전량 노출**이라
읽는 사람이 옛 사실을 현재로 오독한다.

### 수정안 — A③ 교훈 "스테일은 본문 강등"

`stale === true`면:
1. **본문 접힘**(종합 관찰 포함 전부). 펼침은 명시 클릭 1회.
2. 자리에 **스테일 배지**: `2026-07-01 생성 · 당시 6종목 → 현재 4종목 · 39일 경과`
3. 펼쳤을 때 본문 상단에 `당시 기준` 고정 라벨.
4. `다시 분석` 버튼을 배지 옆으로 승격.

### ★한계를 명시한다

**"당시 보유 종목명"은 표시할 수 없다.** `portfolio_advice`가 티커 목록을 저장하지 않고
개수(`holdingsCount`)와 해시(`cacheKey`)만 남긴다. 본문 산문에 종목명이 있으나 LLM 출력이라
파싱은 취약하다(§UI 텍스트 규율).

→ **선택지 (PM 결정 요청)**
- **(a) 개수만** — `당시 6종목 → 현재 4종목`. 프론트만, 백엔드 0. **CC 추천**(스테일 인지에 개수로 충분).
- (b) 백엔드에 `holdingsTickers` 저장 추가 — 정확하지만 `portfolio_advice` 스키마·캐시키 영향.

### 검증 시 주의

`다시 분석` 실행은 **Gemini 호출을 태운다**(§5 비용 규율 — 파이프라인이 유일 소비자가 이상적).
동작 실검증은 하되 **PM이 시점을 지정**해 주기 바란다. 임의로 눌러 쿼터를 쓰지 않는다.

## 3. P③ 자산흐름 차트 — ★설계 전 반드시 짚을 것

### 데이터 실측 (`portfolio_snapshot` 53행, 2026-06-14 ~ 08-09)

```
직전 행과 total_value 동일 :  7행 (13%)
주말 행                    : 15행
결번 구간                  : 06-20→06-23, 06-27→06-30 (각 3일)
payload keys               : fx_rate pnl_pct currency cash_total fx_missing
                             n_holdings asset_total by_currency cash_by_currency
```

### 신규 발견 — 이 시계열은 **성과 곡선이 아니다**

```
날짜         n    주식        현금        총자산
07-30 (목)   6   7,039,952   1,078,559   8,118,511
07-31 (금)   2   2,637,010   6,237,375   8,874,385   ← 주식 −63%, 현금 +478%
08-04 (화)   2   1,363,200   7,147,925   8,511,125
08-06 (목)   4   4,017,555   4,826,471   8,844,026
```

`n_holdings`가 6→2→3→2→3→4로 함께 움직인다 → **데이터 버그가 아니라 실제 매매다.**
그러나 그 결과:

- **주식 평가액 라인**은 매매 때마다 계단으로 꺾인다. 수익률로 읽으면 완전한 오독이다.
- **총자산 라인도 안전하지 않다.** 07-31에 주식 −4,402,942 / 현금 +5,158,816 로
  **차액 +755,874가 생기고 총자산이 그만큼 뛴다**. 현금은 KPH 수동 입력이라 매도대금 반영
  시점이 어긋나면 총자산이 튄다. 즉 **입출금·수동 현금 수정이 곡선에 섞여 있다.**

### 그래서 — 만들지 않을 것부터

**TWR(시간가중수익률) 같은 성과지표를 만들지 않는다.** 입출금 시점·금액 데이터가 없어
정직하게 계산할 수 없고, 없는 걸 추정하면 그게 §F7 위반보다 나쁜 "그럴듯한 거짓"이 된다.
새 계산 로직 신설은 이번 범위 밖이며, 필요하면 별도 PR·PM 승인 사항이다.

### 차트안 (표시 전용, 계산 0)

- **주선 = 총자산(`asset_total`)** 1개. 보조선 = 주식 평가액(옅게).
- **캡션 필수**: `매매·입출금·현금 수정이 포함된 잔고 추이입니다 — 수익률이 아닙니다.`
- **`n_holdings` 변화일에 점 마커** + 툴팁 `6종목 → 2종목`. 계단의 원인을 그 자리에서 설명한다.
  (PM 지적처럼 "숨기지 않기"의 가장 정직한 형태)
- **시작일 명시**: `2026-06-14부터 (53일)`. 이력이 짧은 걸 축으로 감추지 않는다.
- 기간 토글 `1M / 전체`.

### 주말 중복 처리 (CC 질문 ②에 대한 답)

**평탄 유지 = 제외하지 않는다.** 근거:
1. 중복은 **13%(7행)뿐**이다. PM이 본 08-08=08-09는 전형이 아닌 한 사례다.
2. **총자산은 비거래일에도 바뀔 수 있다**(현금 수동 수정). 거래일만 남기면 그 변화가 사라진다.
3. 이력이 53일뿐이라 표본을 더 줄일 이유가 없다.
4. 라인 차트에서 평탄 구간은 시각적으로 이미 "변화 없음"으로 정확히 읽힌다.

## 4. P④ 국내/해외 분리 + 비중%

`by_currency`가 이미 통화별 `n / eval / cost / pnl`을 준다.

- 보유 테이블을 **KRW 그룹 / USD 그룹**으로 나누고 그룹 헤더에 소계(원화 환산 병기).
- 그룹 헤더에 **적용 환율·기준시각** 1회 표기(§R6 — 환율은 `db.latest_usdkrw` 단일 소스가 export한 값).
- 탭 전환이 아니라 **한 화면 2그룹**을 택한다. 탭이면 전체 비중 감각이 끊긴다.

### 비중% (CC 질문 ③에 대한 답) — **찬성**

1. **CLAUDE.md가 이 탭의 소관으로 이미 지정**했다 — 신규-D: "비중·집중도 **관리**(목표비중·
   리밸런싱)는 포트폴리오 탭(5-C) 소관이지 종목 카드가 아니다."
2. **백엔드에 이미 있다.** `stock.actionAdviceLatest.currentWeight`(현대해상 10.56 실측)가
   계산·저장돼 있고 종목 카드에서만 숨긴 값이다 — 신설이 아니라 **보존된 값의 제자리 사용**이다.
3. 홈과 중복 아님: 홈 1열은 종목별 손익, 여기는 자산 구조.

**단, 표시 규율**:
- 분모를 반드시 명시한다 — `총자산 대비(현금 포함)`. 현금 54%인 포트폴리오라 분모가 바뀌면
  숫자가 두 배 달라진다.
- **목표 비중·리밸런싱 지시는 이번 범위에서 제외**한다. 현재 비중 "사실"만 표시(§2).
  `targetWeightLow/High`는 저장돼 있으나 표시하지 않는다 — 지시어가 되기 때문이다.
